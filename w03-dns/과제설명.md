# Week 3 DNS 실습 정리

이번 실습에서는 도메인 이름이 IP 주소로 바뀌는 과정을 직접 따라가고 CDN이 DNS 응답을 어떻게 활용하는지 측정했다. 끝으로 TTL을 지키는 DNS 캐시를 구현해 정확성과 성능을 함께 확인했다.

## Task 1. 반복적 DNS resolver 구현

`task1_resolve.py`에는 루트 DNS 서버부터 시작하는 반복적 resolver를 구현했다. 서버가 최종 A 레코드를 주지 않고 NS 위임을 반환하면 다음 서버로 이동하며 응답하지 않는 서버는 건너뛴다. CNAME을 만나면 대상 이름을 루트부터 다시 조회한다. 반복 조회가 끝없이 이어지지 않도록 최대 깊이도 제한했다.

위임 응답에 glue A 레코드가 없을 때는 NS 이름의 주소부터 별도의 DNS 탐색으로 찾는다. `www.stanford.edu` 조회에서는 이 과정에서 21번의 추가 질의가 필요했고 전체 질의 횟수는 27번이었다. 검증용 도메인 5개는 모두 정상적으로 해결됐다.

## Task 2. DNS 패킷과 CDN steering 측정

`www.korea.ac.kr`을 조회하는 동안 DNS 패킷 6개를 직접 캡처했다. 패킷 1과 2는 transaction ID `23812`를 공유하는 질의와 응답이다. 패킷 2는 answer가 없고 authority와 additional 레코드를 담은 위임 응답이며 패킷 6은 `163.152.6.10`을 반환하는 최종 A 응답이다. 가장 큰 응답은 루트 위임 정보를 담은 패킷 2로 352바이트였다.

12개 사이트는 기존 Wi-Fi와 휴대폰 핫스팟에서 각각 측정했다. 각 네트워크에서 시스템 resolver, Google DNS, Quad9에 질의해 CNAME 체인과 주소 집합을 저장했다. 최종 CNAME의 마지막 두 라벨이 원래 사이트와 다르면 제3자 CDN으로 판단했다. 다만 이 규칙은 `www.wikipedia.org`을 잘못 분류한다. `wikimedia.org`로 이어져 제3자처럼 보이지만 같은 Wikimedia 프로젝트가 운영하기 때문이다.

CDN을 사용하는 것으로 분류한 11개 사이트 중 8개가 resolver 또는 네트워크에 따라 다른 주소 집합을 반환했다. 이 결과는 DNS steering이 실제로 일어난다는 주장과 대체로 맞지만 반환 주소가 지리적으로 가장 가까운 서버라는 사실까지 증명하지는 않는다.

## Task 3. TTL 기반 DNS 캐시

기준 캐시는 모든 레코드를 실제 TTL과 관계없이 60초 동안 보관한다. 그래서 TTL이 60초보다 짧은 레코드는 만료된 뒤에도 반환하고 TTL이 긴 레코드는 아직 유효한데도 다시 조회한다. 개선한 캐시는 이름별로 주소와 만료 시각을 딕셔너리에 저장하고 유효한 항목은 재사용하며 만료된 항목만 upstream에서 갱신한다.

1,000개 질의를 재생한 결과 기준 캐시는 upstream 질의 325회, stale 응답 266회를 기록했다. 개선한 캐시는 upstream 질의를 275회로 줄이면서 stale 응답을 0회로 만들었다. 275회는 이 workload에서 가능한 최솟값이다. 각 이름은 최초 요청과 TTL 만료 후에 반드시 다시 조회해야 하며 그 사이의 유효한 응답은 이미 모두 재사용하고 있기 때문이다. 기준 캐시가 가장 나쁘게 처리한 항목은 TTL이 20초인 `www.microsoft.com`으로, stale 응답이 189회 발생했다.
