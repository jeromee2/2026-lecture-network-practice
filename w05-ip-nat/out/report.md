# 5주차 실습 보고서 — IPv4 주소, NAT, DHCP

이번 실습은 주소와 경로를 계산하는 코드를 만든 뒤, 실제로 연결한 두 네트워크의 주소를 확인하고, 마지막으로 경로 검색 속도를 개선하는 순서로 진행했다.

## 1. 서브넷 계산과 경로 선택

`task1_forward.py`의 `parse_cidr`는 IPv4 주소의 네 옥텟을 32비트 정수로 합치고, 접두사 길이에 맞는 비트 마스크로 네트워크 주소인지 검사한다. 접두사 길이가 0~32를 벗어나거나 호스트 비트가 남아 있으면 거부하도록 했다. `network_range`는 같은 마스크로 브로드캐스트 주소와 사용 가능한 주소 범위를 구한다. `/31`은 두 주소를 모두 사용할 수 있는 지점 간 링크로, `/32`는 한 주소만 있는 경우로 처리했다.

포워딩 테이블은 등록된 경로를 돌면서 목적지와 일치하는 접두사 중 가장 긴 것을 고른다. 예를 들어 `10.20.30.70`은 기본 경로와 `10.0.0.0/8`, `10.20.0.0/16`, `10.20.30.0/24`, `10.20.30.64/26`에 모두 들어간다. 이때 가장 구체적인 `/26`의 다음 홉을 반환한다. 접두사 길이가 같은 경로가 중복되면 먼저 등록한 항목을 유지했다. `python3 task1_forward.py --verify`의 10개 사례가 모두 통과했고, `/31`·`/32`와 잘못된 CIDR 입력도 따로 확인했다.

## 2. 두 네트워크에서 확인한 주소

처음 연결에서는 `task2_myaddr.py --collect "current network"`로 `ifconfig` 결과를 저장했다. 기본 게이트웨이와 외부에서 보이는 주소도 확인했다. 이후 휴대폰 테더링으로 바꿔 `--collect "phone tethering"`을 다시 실행했다. 두 결과는 `out/addresses.json`에 각각 다른 이름으로 남겼다.

| 항목 | 첫 번째 연결 | 휴대폰 테더링 |
|---|---|---|
| 인터페이스 IPv4 / 마스크 | `172.16.31.96/24` | `192.0.0.2/32` |
| 기본 게이트웨이 | `172.16.31.1` | `192.0.0.1` |
| 외부에서 확인한 IPv4 | `163.152.233.31` | `118.235.94.31` |

첫 번째 연결의 마스크는 `255.255.255.0`이다. 직접 계산한 네트워크 주소는 `172.16.31.0`, 사용 가능한 범위는 `172.16.31.1`~`172.16.31.254`, 브로드캐스트 주소는 `172.16.31.255`다. Task 1의 `network_range("172.16.31.0/24")`로 다시 확인했다. 게이트웨이 `172.16.31.1`도 이 범위에 있다. 내 주소 `172.16.31.96`은 RFC 1918 사설 주소인데 외부에서는 `163.152.233.31`로 보였다. 따라서 NAT가 적어도 한 번 일어난다. 다만 이 두 주소만으로 NAT 장비가 정확히 몇 대인지는 알 수 없다. 게이트웨이의 외부 주소나 상위 경로를 더 확인해야 한 단계인지 두 단계인지 구별할 수 있다. 상위 링크에서 `100.64.0.0/10` 주소가 확인된다면 통신사급 NAT의 단서가 된다.

테더링에서는 마스크가 `255.255.255.255`라서 `192.0.0.2/32`의 주소 범위는 `192.0.0.2` 하나뿐이다. `network_range("192.0.0.2/32")`도 첫 주소, 끝 주소, 브로드캐스트 값으로 같은 주소를 반환했다. 게이트웨이 `192.0.0.1`은 이 `/32` 범위 밖에 있지만, 라우팅 테이블에 `en0`으로 이어지는 `192.0.0.1/32` 직접 연결 경로가 따로 있었다. 그래서 게이트웨이에 도달할 수 있다.

`192.0.0.2`는 RFC 1918 사설 주소도 공인 주소도 아니다. [RFC 7335의 IPv4 서비스 연속성 주소 대역 `192.0.0.0/29`](https://datatracker.ietf.org/doc/html/rfc7335)에 속한다. 인터페이스에는 `clat46`과 NAT64 접두사도 표시됐다. 이는 [464XLAT](https://datatracker.ietf.org/doc/html/rfc6877) 구성의 단서이며, 이를 일반적인 NAT44 두 단계로 세면 실제 동작을 잘못 설명하게 된다. 네트워크를 바꾼 뒤 로컬 주소와 외부 주소가 모두 달라진 이유도, 로컬 주소를 부여하는 방식과 외부로 나가는 변환 지점이 함께 달라졌기 때문이다.

## 3. DHCP 패킷 확인

내 장비의 DHCP 교환은 직접 캡처하지 않고 과제에서 허용한 경로 B를 사용했다. 교재 저자의 9판 공식 파일 `../../traces/dhcp-wireshark-trace1-1.pcapng`을 내려받아 `tcpdump`로 읽었다. 같은 트랜잭션 ID `0x56f415ed`로 묶인 Discover, Offer, Request, ACK 네 메시지를 확인했다.

Discover의 출발지는 `0.0.0.0:68`, 목적지는 `255.255.255.255:67`이었다. 클라이언트가 아직 IP 주소를 받지 못했으므로 출발지에 자기 주소를 쓸 수 없고, 서버를 찾으려고 브로드캐스트한다. 서버는 `192.168.86.1:67`에서 Offer와 ACK를 보냈다. 제안한 주소는 `192.168.86.65`, 임대 시간은 86,400초(24시간), 갱신 시점은 그 절반인 43,200초(12시간)다. 이 trace의 ACK는 `192.168.86.65:68`로 유니캐스트됐다. 이때는 할당할 주소가 정해져 있으므로 Discover 때와 달리 특정 클라이언트를 목적지로 지정할 수 있다.

공식 trace 출처: J.F. Kurose와 K.W. Ross, *Computer Networking: A Top-Down Approach*, 9판의 [Wireshark Lab 자료](https://gaia.cs.umass.edu/kurose_ross/). Copyright 1996–2025 J.F. Kurose, K.W. Ross. All Rights Reserved.

## 4. 경로 검색 개선과 확인

`task3_lpm.py`에서는 경로를 접두사 길이별 딕셔너리에 넣었다. 조회할 때 긴 접두사부터 확인하고, 처음 일치하는 항목에서 멈춘다. 경로 수가 늘어도 검사할 접두사 길이는 최대 33개이며, 저장 공간은 경로 수에 비례한다. 비트를 따라가는 트라이도 가능한 방법이지만, 이번 Python 측정에서는 내장 딕셔너리를 이용했다.

`python3 bench.py --yours`로 경로 5,000개와 질의 20,000개를 측정했다. 기존 선형 검색은 조회에 6.990초, 개선한 테이블은 0.010초가 걸려 713.2배 빨랐다. 20,000개 답은 모두 같았다. `python3 ../check.py w05`도 제출 파일 형식 검사를 통과했다. 다만 `test_tasks.py --task 2`는 공식 trace를 쓰는 경로 B를 반영하지 않아 `out/dhcp.pcapng`이 없다는 한 항목을 실패로 표시한다. 직접 캡처한 파일처럼 꾸미지 않고, 사용한 자료와 경로를 보고서에 밝혔다.
